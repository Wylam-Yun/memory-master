# Memory Master 前端信息架构与 UI/UX 研究

日期：2026-11-05。基线：`86f3e07a`。状态：独立重规划建议，供用户审阅，尚未实施。

本研究仅以 Memory Master 当前仓库与已明确的普通用户需求为产品依据。外部网站只提供视觉与交互参考，其业务、功能和架构不构成本产品需求。前序五页排布是待重新评估的输入，不作为本次结论的前提。

## 1. 结论与产品工作方式

用户已明确收简：采用五个项目页面——概览、任务、项目架构、资料、变更记录。网页不设置待决定板块，任务不加入验收项或负责人。人需要拍板时，Agent 直接在当前 Codex 或 Claude Code 对话询问，并根据答案维护项目。

推荐单侧栏项目工作台：项目切换在侧栏顶部，低频设置在底部，主区每次只呈现当前页。概览是一份可读的说明，任务是名称加状态的简单列表，资料点击文件名就在网页查看，架构帮助理解组成与关系，变更记录用于复盘。

保留 P0/P1：网页只展示 P0，Agent 可维护两类。项目架构仍适用于通用项目，无需代码目录。产品内不新增聊天窗口。此前独立待决定入口及复杂任务详情的建议已取消，不能作为实施要求。

### 2.3 已观察到的问题

1. **阅读被编辑器阻挡。** `App.tsx:301` 使用 `rows={2}`。隔离项目实测三框显示高均为56px，内容高176/116/296px，全部发生内滚动。应先展示正文，编辑作为明确动作。
2. **页面职责过多。** `ProjectPage` 一次读取全部五类数据，页面顺序由组件堆叠决定。用户找到提问与历史依赖长距离滚动。
3. **任务完成操作不够直观。** 标题后只有状态和「推进」，点击结果不够明确；应直接勾选完成或选择明确状态，不为普通用户增加任务管理表单。
4. **资料对人不完整。** 上传成功后人只能看到文件名。Agent可以读，用户却不能在同一产品核对它读的原件，不符合共同管理定位。
5. **历史压过最新状态。** 每条记录默认展开所有前后值，概览一次长文更新会再次制造大段正文。
6. **过多低对比小字。** 问题正文、回答、文件名、历史差异等核心信息大量使用 `text-xs` 和浅灰。缩小核心信息并没有减少其认知成本。
7. **编辑与协作状态不稳。** 源码显示每次写入后整体load，版本冲突也load并替换overview，存在覆盖本地草稿的路径；本项为源码判断，尚未做冲突浏览器复现。
8. **技术配置占据日常注意力。** 项目列表默认暴露绝对路径，设置默认展示token；普通用户首先需要知道项目名称、保存位置与连接结果。
9. **新数据不会自然出现。** 当前项目页主要在挂载和写入后重载，设置连接态也缺少持续更新；Agent在另一会话写入后页面可能陈旧。需设计更新提示与保留草稿机制。

## 4. 三个布局候选

三案使用相同的项目作用域与内容模型，只比较导航和空间分配；实施时选一个，无需同时维护三种布局。

| 方案 | 组合 | 优点 | 代价与适用条件 |
| --- | --- | --- | --- |
| A 单侧栏项目工作台（推荐） | 224px侧栏：项目切换、项目导航、底部设置；主区阅读；详情按需打开 | 五类目的地文字完整，项目作用域稳定，页面可继续扩展；适合电脑与后续桌面应用 | 消耗少量横向空间；窄窗口改顶部菜单，避免压缩正文 |
| B 顶部项目页签 | 全局顶栏＋项目选择＋横向项目页签＋主区 | 宽图和阅读获得更多横向面积，小功能集直观 | 五个中文页签和项目切换在窄窗口容易挤压，需两行或滚动；长项目名时较吃力 |
| C 文档中心 | 概览为主，任务/资料主要通过正文入口与二级页面访问 | 界面最安静，适合主要是阅读的低频项目 | 任务状态更隐蔽，日常反复跳转，随内容增长不易发现新入口 |

推荐A，原因是当前项目的差异来自「人和Agent接手同一份状态」，既要阅读也要简单维护任务。C牺牲行动可发现性，B更适合页面类型长期更少的产品。A只使用一条侧栏，不再常驻项目列表第二栏或右侧仪表盘。

### 与原排布相比，哪些合并、哪些拆开

- 网页取消待决定板块，包括任务内问题标签与未回答角标；需要用户拍板时在Agent聊天中完成，不将它移到另一处隐藏页面。
- 保留「概览」与「项目架构」分开：前者连续阅读最新说明，后者需要画布、节点选择和放大。概览只留一个普通文字入口，不嵌入缩略仪表盘。
- 合并「Agent连接」与「记忆库位置」到设置：二者是应用级配置，不属于单个项目的内容，不做独立Agent管理产品。
- 资料列表与资料阅读为主从关系，新增项目只用短弹窗，不增加独立编辑站点。
- 不设「首页仪表盘」「统计」「消息中心」「知识库编辑器」。现有字段不足以支撑可信的进度百分比、实时在线或自动摘要。

## 6. 关键布局决策及理由

| 决策 | 理由 | 如何核对 |
| --- | --- | --- |
| 默认进入概览，简介后紧接当前进展 | 新接手先知道对象，再知道现状；长期目标不挤掉今天重点 | 首次阅读者能回答用途、当前工作和下一步 |
| 任务只有名称和状态，需要拍板时回到当前聊天 | 降低普通用户的学习成本，保持原有聊天协作方式 | 无验收清单、负责人或问题板块，能够直接勾选任务 |
| 日常任务只显示P0，已完成默认折叠 | 遵守用户约束并控制列表长度，保留复验入口 | 混合P0/P1数据下逐条检查，不以总数掩盖遗漏 |
| 主要页面无常驻右栏 | 大多数右栏元数据低频，持续占宽会迫使正文变窄 | 1024px仍能阅读16px正文；详情仅在需要时展开 |
| 任务和资料用行列表 | 数据需要纵向扫描和比较，等高卡片浪费空间 | 30条任务/资料仍能分辨标题与状态 |
| 只在对象边界用面板或卡片 | 卡片用于选择与浮层，非给每个段落套框 | 概览正文不出现嵌套卡片，空状态只出现一次 |
| 编辑显式保存，切页保留草稿 | 多Agent会并发改状态，不能用静默覆盖换取表面流畅 | 本地草稿＋外部新版本可比较后再提交 |
| 专项扩展附着通用内容 | 不要求普通用户选类型或理解专业结构 | 无目录项目完整走完创建、资料、任务更新和接手 |

## 7. 依赖、实施建议与待确认

### 可先做的整理

基于现有数据拆出概览阅读、简单任务、资料列表、历史与设置；统一字体和间距；增加草稿保护、明确状态操作、局部错误与重新读取。不要先改变存储模型来完成外观工作。

### 必须补接的数据能力

1. 仅把任务优先级贯穿库 API、MCP和网页；名称、状态与可选描述沿用已有能力。勾选表示整条完成，不新增验收项或负责人；合法状态以配置为准。
2. 概览功能与用法字段、通用项目架构的版本化读写。

## 8. 验收研究方案的方法

先用线框图做一次任务走查，再做高保真稿；用户确认结构后才改产品。建议邀请3–5位目标普通用户进行形成性测试，该数量是实际执行建议，不是统计显著性保证。

- 找项目并说明项目用途、当前重点和下一步；记录是否走错入口。
- 需要拍板时在当前Agent聊天中提问与回答，后接手Agent能从更新后的项目说明或任务读到结论；网页不出现问题板块。
- 找到一条P0任务，直接勾选整条任务并核对状态；确认P1未混入。
- 上传一份资料并由人查看同一原件，再让Agent读取；核对名称与内容。
- 人编辑概览期间由另一Agent更新；本地草稿不丢，选择合并后重读磁盘与网页。
- 在320/390/768/1024/1440px、200%缩放与键盘下逐项走查。结构画布可二维移动，普通正文不需要横向滚动。
- 停用客户端后实际MCP拒绝读写；应用关闭后界面明确不可用。不能只凭开关变灰或出现成功提示判断生效。
