# MCP 跨项目错写修复提案

状态：已实现并验证。所有项目内容读写必须显式指定 project_id，旧调用缺少 ID 时直接拒绝。

在隔离服务创建只读项目 A 和可写项目 B。用同一 `LibraryBridge` 会话依次打开 A、读取 A、打开 B，再提交原本属于 A 的 `task_create`。当前分支返回写入成功。核对磁盘后 A 有 0 份任务文件，B 有 1 份，标题为 `Intended for A`。这个调用顺序可以稳定重现真实 Claude Code 会话中的并行项目切换。

`project_open` 保存一个会话共用的 `selectedProject`。`task_create` 请求没有项目 ID，发送时从 `selectedProject` 取目标。打开 B 覆盖了 A，服务收到的是项目 B 的写请求，因此按 B 的授权处理。单个工具排队仍允许 `打开 A → 打开 B → 写入`，无法从无项目 ID 的写入推断用户意图。

| 方案 | 代价与范围 |
| --- | --- |
| 所有项目读写显式携带 `project_id`（推荐） | 读写目标都由当前请求指定，跨项目调用可并行。旧调用缺 ID 时明确失败，客户端需要刷新工具定义并更新调用参数。 |
| 只要求写入携带 `project_id` | 旧读取可以继续使用，但并行读取仍可能拿错项目的内容或版本，影响后续操作。 |
| 一个连接只允许绑定一个项目 | 单项目旧工作流保留。切换要重建连接；失败的切换也必须让无目标调用停止，避免工具沿用旧项目。 |

采用推荐方案时，按以下步骤实施。

1. 在真实 HTTP 服务与 MCP 桥接之间补上回归用例。A 只读，B 可写，先读 A，再让同会话切到 B。分别断言无 `project_id` 的调用在桥接层拒绝、显式写 A 返回 `WRITE_DISABLED`、A 与 B 两个项目的文件和变更记录均未被上述请求修改。最后显式写 B，核对只在 B 新增一条记录。
2. 在 `src/mcp/library-bridge.ts` 为项目内容工具统一声明必填 `project_id`。根据请求参数构造服务端路径；缺失、空值或类型错误在发请求前拒绝。`project_list` 和 `project_open` 继续查找项目，返回可用于调用的 ID；`project_current` 仅报告会话选择。
3. 更新 `src/library/agent-content.ts` 及随客户端安装的 Agent 文档，说明从查找结果保存目标 ID，在之后的读写中复用同一个 ID。更新已有桥接测试、工具契约检查、README、用户指南、架构与 CHANGELOG。
4. 核对任务、概览、架构、目标、阶段进展、问题、资料和历史的全部项目工具声明与执行路径。运行项目空间测试，然后用编译版 stdio MCP 和真实 Codex、Claude Code 重测同会话交错调用。验收以工具返回状态及 A、B 独立的磁盘终态为准。

## 验收结果

- 回归测试在修复前捕获了 B 项目新增的任务文件和变更记录。修复后，缺少项目 ID 和显式写只读 A 都不会改变任一项目；只有显式写 B 会新增任务。交错读取分别返回 A、B 各自的概览。
- 项目空间测试 130 项通过，0 失败；类型检查、编译及编译产物启动检查通过。
- 实际编译版 stdio MCP 的全部 22 个项目内容工具均声明且强制要求顶层项目 ID。以有写权限的项目验缺失 ID，22 个请求均返回 `PROJECT_ID_REQUIRED`，任务目录为空；显式指定后任务实际落盘。
- Codex CLI 和 Claude Code 各在同一个真实会话先打开 A、后打开 B，再分别显式读取 A、B 并尝试写入。两边均收到各自项目内容；写 A 返回 `WRITE_DISABLED`，A 文件和变更记录未变；B 只新增一份预期任务。两边 CLI 均正常退出。工具调用记录保存在本机临时目录 mm-target-live-evidence-vn_3htn4。
