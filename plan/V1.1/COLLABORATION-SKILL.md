# Memory Master 项目协作

本文件是 V1.1 协作 Skill 草案，供审阅及 R3 安装接入使用。目前不表示已经替换本机客户端的 Skill。

维护的是人和多个 Agent 共用的项目记录。读者可能第一次接触这个项目，也可能不知道相关技术。用自然语言说明实际对象、动作和结果；必要术语首次出现时解释含义。让读者只看项目记录就能知道项目是什么、目前做到哪、接下来做什么。

## 接手与项目归属

1. 用户明确给出项目名称或 ID 时，用实际可用的 `project_open` 打开。名称有歧义时向用户确认候选。本会话保持所选项目，用户明确切换前不改选。
2. 读取 `overview_read`、`task_list`，接手续作时看近期 `history_list`；按任务需要用 `resource_list`、`resource_read` 读取用户选入的资料。已有问题记录仅在需要核对先前答案时读取。
3. 写任何项目正文前，必须读 [内容标准](CONTENT-STANDARD.md) 的「共同写作规则」和本次涉及的板块；已经读过且未变化时可继续沿用。整理架构前再读 [架构格式](ARCHITECTURE-FORMAT.md)。
4. 无工作目录的项目照常管理。读取额外本地文件需要明确的位置，当前目录不能自动决定项目归属。临时杂事不写入项目。

## 每个板块写什么

| 板块 | 写入或维护标准 | 何时更新 |
| --- | --- | --- |
| 所有项目 | 名称要让用户辨认正在管理的事情；沿用用户确认的项目名称，不用ID、目录名或代号代替。列表是系统展示，不手写一份项目目录清单。 | 用户明确新建或改名时；只使用实际提供的工具，不自造项目创建接口。 |
| 概览·简介 | 用完整句子说清为谁做、解决什么问题、主要怎样使用。不能只写几个技术名词。 | 项目刚建立，或用户确认定位变化时。 |
| 概览·当前进展 | 写当前已完成的结果、正在推进的工作、确实存在的阻碍和下一步。区分计划、已实现和已验证，保留一份最新摘要。 | 接手有实际状态变化、阻塞、解除阻塞、完成关键工作时。 |
| 概览·目标 | 说明最终希望用户能完成什么、看到什么效果。目标可以尚未达成，不把它写成已具备能力。 | 用户确认新增、删减或改变范围时。 |
| 概览·功能与用法 | 每项先说现在能做什么，再写从哪里开始、按什么步骤做、完成后看到什么。普通项目可说明已有成果的使用方法。 | 能力或交付内容确认可用，或入口、步骤、限制变化时。 |
| 任务 | 名称写清动作和对象，维护待开始、进行中或完成状态。仅必要时补一句说明。不增加验收清单、负责人或复杂任务表单。 | 开始推进、出现阻塞、解除阻塞、实际完成时；状态使用项目支持的值。 |
| 项目资料 | 先读取原件，再引用准确文件名并用一句话说明与当前工作的关系。原件由用户选择上传，默认不改原文、不自动收集工作文件。 | 用户选入资料或需要修正引用时。 |
| 项目架构 | 解释项目由哪些部分组成、各部分做什么、它们怎样衔接。图、名称与自然语言说明一起维护；既支持通用流程，也支持用户明确要求的专业架构。 | 主要组成、职责、关系或流程变化时。 |
| 变更记录 | 成功修改由系统记录操作者、时间与前后值。Agent提交真实字段即可，不另填原因、证据链接或另写一套历史。 | 每次成功写入自动发生；Agent按需读取复盘。 |
| 设置 | 名称、位置、授权开关与接入状态来自真实配置；这里只需向用户说明怎么操作，不编写或伪造配置状态。 | 用户询问配置，或连接、权限出现问题时。 |

概览显示顺序为简介、当前进展、目标、功能与用法。P0是当前重点，网页只展示P0；P1是后续安排，保留供Agent维护。以用户确认的重点安排优先级，不把所有想法都升级为P0。新建普通任务默认P0，明确的后续安排指定P1。

任务完成意味着整条工作实际完成。仅有计划、代码或草稿时，保持真实的未完成状态；无需用户填写额外验收表。写作示例和好坏对照见内容标准，示例不是当前项目事实。

## 主动与用户协作

在当前 Codex 或 Claude Code 对话里，直接提出会影响结果的具体问题。先说明缺少什么，再给用户能回答的选择或问题；普通执行细节自行处理。用户给出答案后，更新相关概览或任务，让后接手的 Agent 看得到结论。

网页只保留概览、任务、项目架构、资料、变更记录五页。不要恢复待决定板块、问题标签、未回答角标、任务验收项或负责人。已有问题数据保持兼容，读取旧答案不等于恢复问题管理页面。

## 更新与保存

1. 确定此次真实变化，只更新受影响内容。无实质变化时不制造重复记录；用户写的其他内容保留。
2. 先读最新记录和版本，按实际工具 schema 提交，更新带 `base_version`。收到 `VERSION_CONFLICT` 时重新读取、比较双方内容后再决定如何合并。
3. 工具未支持某字段、优先级或架构保存时，明确说明该部分尚未写入，把拟补内容留在本次回复中；不绕过服务手改记忆库，也不假装调用了不存在的工具。
4. 写入成功后重读，核对目标项目、正文和状态确实保存。界面操作涉及文件或其他外部结果时，再核对真实结果；工具调用返回成功不能替代实际效果。
5. 完成前检查相关的进展、任务、功能与用法、架构是否需要一起更新。只同步发生变化的内容，向用户简短说明已保存结果及仍未完成的工作。

## 提交前的文字检查

- 第一次看项目的人，能否从这段文字知道对象、动作、结果与下一步？缺少背景时补必要的一句解释。
- 是否把技术动作写成了用户已经能使用的功能？未验证的部分明确写出范围。
- 功能说明是否包含真实入口和步骤，任务名称是否指出具体要做什么，架构箭头是否说清两部分的关系？
- 是否混入本次聊天流水、无关项目、未经用户选入的资料、实施代码或细节？按项目管理范围收敛。
- 用实际含义检查，不要求固定字数，也不为凑模板生成无内容的小标题。避免用比喻替代解释。

## 连接和权限

服务不可达时说明需要打开 Memory Master 应用；客户端被停用时说明需要由用户在设置中重新允许访问。启用、配置完成和实际接入是不同状态，按服务返回解释；不把最近接入时间说成实时在线或正在工作。设置和凭据不属于项目正文，不把它们复制进概览、任务或资料。
