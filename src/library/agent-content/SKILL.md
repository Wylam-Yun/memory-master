# Memory Master 项目协作

维护的是人和多个 Agent 共用的项目记录。读者可能第一次接触这个项目，也可能不知道相关技术。用自然语言说明实际对象、动作和结果；必要术语首次出现时解释含义。让读者只看项目记录就能知道项目是什么、目前做到哪、接下来做什么。

## 接手与项目归属

用户在聊天中要求建立项目，或讨论一项需要持续保存进度的工作且尚未选定项目时，先按下面的流程确定归属。

1. 用 `project_search` 查询用户话题的简短关键词。用户明确提供本地目录时一并传 `working_dir`，用关联目录查找同一项工作。需要时换关键词再次查询；措辞差异较大时用 `project_list` 查看名称，并按需打开候选读取正文，判断内容是否相关。搜索提供文本匹配，语义相关性由聊天中的 Agent 判断。
2. 发现潜在相似项目时，在当前聊天说明候选名称、相关内容及相似原因，询问“要更新这个已有项目，还是新建一个项目？”等待用户选择后再写入。查询候选保持当前项目选择；为阅读而打开其他项目后，恢复原项目。用户已经明确指定已有项目时直接打开，无需再次询问归属。
3. 用户明确要求新建时，使用用户给出的名称调用 `project_create`；未命名时先提出可辨认的名称并确认。可传用户明确提供的已有绝对目录。创建成功即选中项目，随后读概览与任务，按内容标准整理本次对话中已确认的背景、决定和下一步。创建超时先查列表核实是否已成功，重名时读取已有项目并让用户决定。
4. 用户只是在讨论潜在工作、尚未要求保存时，先在聊天确认是否建立或更新项目。用户选定已有项目后，先读最新正文再合并已确认的内容，保留仍有效的记录。
5. 用户要求关联、更换或解除本地目录时，用 `project_open` 或 `project_current` 读取目标项目的 `id`、最新 `workingDir` 和项目配置 `version`，再调用 `project_update` 并显式传入 `project_id`，`base_version` 使用该配置版本。`working_dir=null` 解除关联。概览版本和项目配置版本分别使用。项目移动后按用户提供的新路径更新关联。

选定项目后按以下步骤接手。

1. 用户明确给出项目名称或 ID 时，用实际可用的 `project_open` 打开。名称有歧义时向用户确认候选。保存返回的 `opened.id`。每个项目内容工具都要求顶层 `project_id`；读取、写入、重读核对都传目标项目的同一个 ID。处理多个项目时分别保存 ID，按项目配对 `base_version`。
2. 先读 `overview_read` 的当前进展和当前目标，再用 `task_list` 找到相关任务。按任务需要查完整简介、约定、`criticalPaths` 和近期 `history_list`；需要回顾已完成/已调整目标时用 `goal_list`，阶段成果用 `progress_list`，按需分页；按任务需要用 `resource_list`、`resource_read` 读取用户选入的资料。已有问题记录仅在需要核对先前答案时读取。
3. 写任何项目正文前，必须读 [内容标准](CONTENT-STANDARD.md) 的「共同写作规则」和本次涉及的板块；已经读过且未变化时可继续沿用。整理架构前再读 [架构格式](ARCHITECTURE-FORMAT.md)。
4. 无工作目录的项目照常管理。读取额外本地文件需要明确的位置，当前目录不能自动决定项目归属。临时杂事不写入项目。

接手或生成交接说明前，再读[内容标准的「接手与交接」](CONTENT-STANDARD.md#接手与交接)。按用户本次要继续的事情组织上下文，只引用相关资料；用户已要求继续时直接推进已授权工作。

## 名称与网页一致

人和Agent读取同一份正文，统一使用项目简介、当前进展、目标、功能与用法、项目约定、关键路径、阶段进展这些名称。网页的「最新进展」取自当前进展正文。阶段进展中的每条记录是一项关键成果。简报是当前进展的写法，不另建交接摘要、接手报告或另一份进度。

正文直接写该板块的实际内容，网页已提供名称时不在正文开头再重复同名标题。简介保留完整背景；功能与用法以具体能力或成果名称为标题，接着写用途与操作步骤；约定保留明确条目；当前进展在同一份Markdown中用“已完成”“当前停点”“未完成或未验证”“下一步”“需要你决定”小标题组织，有内容才写；标题前使用##，前端读取这些实际标题突出显示，不增加另一份摘要。

## 每个板块写什么

| 板块 | 写入或维护标准 | 何时更新 |
| --- | --- | --- |
| 所有项目 | 名称要让用户辨认正在管理的事情；沿用用户确认的项目名称，不用ID、目录名或代号代替。列表是系统展示，不手写一份项目目录清单。 | 用户明确新建或改名时；只使用实际提供的工具，不自造项目创建接口。 |
| 项目约定 | 保存用户已经确认、跨会话仍有效的决定与约束，以及必要的已排除方向和失败尝试。与最新简报分开维护；保留仍然有效的约定，不把建议或旧记录当成新增授权。 | 用户明确决定、修改约束，或确有会影响后续工作的排除结论时。 |
| 项目简介 | 用完整句子说清为谁做、解决什么问题、主要怎样使用。不能只写几个技术名词。 | 项目刚建立，或用户确认定位变化时。 |
| 当前进展 | 重写一份比目标更详细、精准的最新简报：实际结果、当前工作到哪一步、未完成或未验证的范围、下一步。有阻碍才写。保留必要背景，整理替换过时情况。 | 接手有实际状态变化、阻塞、解除阻塞、完成关键工作时。 |
| 目标 | 每条一句话表达希望得到的结果，用goal_create独立创建。客观可验证的目标达成后主动归档；主观目标创建时标记requires_confirmation，得到用户确认后再完成。调整方向保留原目标。 | 新增、达成或用户确认方向变化时。 |
| 阶段进展 | 关键成果实际完成时记录标题、完成日期和较标题详细的结果说明，普通聊天与保存不生成。先查已有记录，同一成果补充原记录。 | 有独立意义的关键成果完成时。 |
| 功能与用法 | 每项先写用途，再给前提、实际入口、可复现步骤、预期结果和已验证范围。最近确认可用的章节排在前面。 | 能力或交付内容确认可用，或入口、步骤、限制变化时。 |
| 任务 | 名称写清动作和对象，维护待开始、进行中或完成状态。仅必要时补一句说明。不增加验收清单、负责人或复杂任务表单。 | 开始推进、出现阻塞、解除阻塞、实际完成时；状态使用项目支持的值。 |
| 关键路径 | 接手开发任务时读取相关路径。用 `overview_write.criticalPaths` 维护名称、用途和位置，格式见[关键路径](CONTENT-STANDARD.md#关键路径)。 | 路径、用途或访问条件实际变化时。 |
| 资料 | 先读取原件，再引用准确文件名并用一句话说明与当前工作的关系。原件由用户选择上传，默认不改原文、不自动收集工作文件。 | 用户选入资料或需要修正引用时。 |
| 项目架构 | 依次写整体说明、关系图、各部分职责和主要流程。职责用完整自然语言，默认直接可读；来源与关联任务仅作可选补充。不写本轮测试过程、接手情况或发布待办，这些放在当前进展和任务。既支持通用流程，也支持用户明确要求的专业架构。 | 主要组成、职责、关系或流程变化时。 |
| 变更记录 | 成功修改由系统记录操作者、时间与前后值。Agent提交真实字段即可，不另填原因、证据链接或另写一套历史。 | 每次成功写入自动发生；Agent按需读取复盘。 |
| 设置 | 名称、位置、授权开关与接入状态来自真实配置；这里只需向用户说明怎么操作，不编写或伪造配置状态。 | 用户询问配置，或连接、权限出现问题时。 |

打开项目先看综合概览。页头副标题取自完整简介，正文优先展示最新进展、当前目标、重点任务和最近确认可用的功能；历史目标、最近完成、关键路径、项目约定和阶段成果按需展开。在概览内展开细节、编辑对应栏目，每次只保存该栏正文。P0是当前重点，网页只展示P0；P1是后续安排，保留供Agent维护。以用户确认的重点安排优先级，不把所有想法都升级为P0。新建普通任务默认P0，明确的后续安排指定P1。

任务完成意味着整条工作实际完成。仅有计划、代码或草稿时，保持真实的未完成状态；无需用户填写额外验收表。写作示例和好坏对照见内容标准，示例不是当前项目事实。

## 主动与用户协作

在当前 Codex 或 Claude Code 对话里，直接提出会影响结果的具体问题。先说明缺少什么，再给用户能回答的选择或问题；普通执行细节自行处理。用户给出答案后，更新相关概览或任务，让后接手的 Agent 看得到结论。

项目左侧有概览、项目架构、资料、变更记录和项目设置。任务页从概览的当前任务进入；需要用户拍板的事项在聊天里问，在最新进展用“需要你决定”提示实际阻塞。


## 动态目标与阶段进展

1. 先读概览和项目约定，判断当前实际变化，保留其他正在推进的工作及仍有效的决定。`overview_write.current`替换一份完整的最新简报；简报比一句话目标详细，用具体结果、边界和下一步帮助接手，不能只写“正在完善”。
2. `goal_create`的`title`写一句话结果，`key`是本次创建的稳定标识，决定时生成并在重试中复用。主观认可的目标传`requires_confirmation=true`。旧`goal`长正文保留为原有目标；逐条整理时只录入明确的目标，不从旧文字猜已完成状态。
3. 目标达成时用`goal_update(status="completed")`主动归档。主观目标先在当前聊天询问，用户确认后才传`confirmed=true`。只有代码、方案或部分检查通过时保留目标正在推进。
4. 方向改变用`goal_update(status="adjusted")`；可带`replacement_title`建立新目标，旧目标与调整日期保留。需要补充旧目标时先读归档，不能把旧目标覆盖成另一项工作。
5. 关键成果完成后用`progress_record`记录阶段结果；可关联已有`goal_id`。目标完成时可以通过`goal_update.progress`与`current`一次保存归档、成果和新简报。先用`progress_list`检查已有成果，同一成果用`progress_update`修正，复用原ID和创建key。
6. 正常完成的日期由软件记录；补录过去成果仅填写实际已知日期。`occurred_at`或`completed_at`省略表示现在，明确未知传null。记录时间不是实际完成日期，不能猜日期。
7. 目标和阶段成果共用概览的版本。每次写入前用`overview_read`或对应列表读取最新`version`，提交`base_version`；冲突时比较后合并，重试仍用原key。归档后重读列表与概览核对目标、成果、日期和最新进展。

关键成果指可独立回顾的实际结果，例如“两个Agent能接手同一个项目”。过程中修改配置、修正措辞和运行检查并入成果，不按工具调用、聊天轮次或每次保存创建汇报。未提供这些工具时说明未归档，遵循下列工具缺失规则。

## 更新与保存

1. 确定此次真实变化，只更新受影响内容。无实质变化时不制造重复记录；用户写的其他内容保留。
2. 先读最新记录和版本，按实际工具 schema 提交，更新带 `base_version`。收到 `VERSION_CONFLICT` 时重新读取、比较双方内容后再决定如何合并。
3. 工具未支持某字段、优先级或架构保存时，明确说明该部分尚未写入，把拟补内容留在本次回复中；不绕过服务手改记忆库，也不假装调用了不存在的工具。
4. 写入成功后重读，核对目标项目、正文和状态确实保存。界面操作涉及文件或其他外部结果时，再核对真实结果；工具调用返回成功不能替代实际效果。
5. 完成前检查相关的进展、任务、功能与用法、架构是否需要一起更新。只同步发生变化的内容，向用户简短说明已保存结果及仍未完成的工作。

## 提交前的文字检查

- 第一次看项目的人，能否从这段文字知道对象、动作、结果与下一步？缺少背景时补必要的一句解释。
- 是否把技术动作写成了用户已经能使用的功能？未验证的部分明确写出范围。
- 功能说明是否包含真实入口和步骤，任务名称是否指出具体要做什么，架构箭头是否说清两部分的关系？
- 是否混入本次聊天流水、无关项目、未经用户选入的资料、实施代码或细节？按项目管理范围收敛。
- 用实际含义检查，不要求固定字数，也不为凑模板生成无内容的小标题。避免用比喻替代解释。

## 连接和权限

服务不可达时说明需要打开 Memory Master 应用；客户端被停用时提示用户在「所有项目 → 全局设置」检查连接。项目未开放时请用户检查「项目设置」，不要把不可见的项目视为已删除。收到 `WRITE_DISABLED` 时说明当前只读，由用户在项目设置里决定是否允许修改；不换凭据或绕过权限。启用、配置完成和实际接入是不同状态，按服务返回解释；不把最近接入时间说成实时在线或正在工作。设置和凭据不属于项目正文，不把它们复制进概览、任务或资料。
