# Memory Master 代码架构维护

本文件是软件架构图专项扩展的设计草案，保留供后续需要时使用。V1.1 通用项目协作由 `memory-master` 应用通用内容标准和项目架构格式完成，不依赖本草案安装。仅在用户明确要求软件架构分析或维护时使用以下源码调查规则，普通项目直接根据用户确认的信息和资料维护项目架构。

产出能帮助用户判断「项目怎样工作、任务影响哪里」的当前架构。源码和实际调用提供事实，用户确认项目目标。参考 [内容标准](CONTENT-STANDARD.md) 和 [架构格式](ARCHITECTURE-FORMAT.md) 编写。

## 1. 确认项目和代码位置

- 有 Memory Master MCP 时，先按用户明确给出的名称或 ID 用 `project_open` 打开项目，再读 `overview_read`、`task_list` 和 `question_list`。保持本次选定的项目。
- 从用户给定的代码路径或已选项目的 `workingDir` 读取代码。记忆库里的项目目录是记忆存储位置，代码位置以用户给定路径或 `workingDir` 为准。
- 创建或核对架构需要用户明确提供的代码位置，或已选项目中可读取的 `workingDir`。缺少时先询问具体路径，等用户提供后再调查代码并生成文件。当前工作目录及其父目录只能在用户明确指定它们时作为代码来源。用户仅要求查看现有架构时直接读取已有内容。
- 临时杂事跳过项目记录。新增功能和重构建议交给用户决定后再进入计划。

## 2. 核对现状

读取实际入口、主要调用、配置和存储路径。更新已有图时，先读取图及其版本，再看本次改动和受影响模块。

每个模块都要找到职责对应的代码，每条连接都要找到调用、配置或数据读写依据。动态关系依据不足时，在「待核对」中说明缺少什么证据。把用户目标和未来方案写在项目目标或计划里，当前架构以已实现的关系为准。

总图按用户能理解的职责归组。需要展开时增加模块细图。模块 ID 随重命名保持稳定，标签使用人能理解的业务名称，代码位置使用相对代码根目录的路径。

## 3. 编写和维护

- 按 [架构格式](ARCHITECTURE-FORMAT.md) 维护一份 Markdown。按整体说明、关系图、模块职责、主要流程组织。图源和组成表保留在同一记录里，网页将组成表显示为默认可读的说明；代码依据和必要核对范围仅作补充，不混入测试流水、接手进度或发布待办。
- 首次生成时建立总图和模块表。普通任务完成时检查模块职责、依赖或数据流是否变化，有变化才改对应内容。名称和连接保持能与现有代码核对。
- 在模块表维护关联的项目任务 ID，任务页从同一份架构记录显示受影响模块。模块移除时，先检查关联任务和细图，说明这些关联的后续去向。
- 无架构变化时，在任务完成反馈里说明已核对即可。已核对的代码版本只代表本次实际查看的范围，局部检查保留其余范围的原核对信息。
- 排布采用清晰层级、充足留白和少量配色。箭头标明具体动作，例如「提交更新」「读取状态」。让总图在普通桌面窗口里可读，复杂内容通过细图展开。

## 4. 验证和交付

先检查图能渲染，再逐模块核对职责和路径，逐连接核对代码依据。检查图中的模块 ID 与模块表一致，节点文字能完整阅读。可用预览工具时实际打开查看。

查看 MCP 工具清单。若存在架构读取和更新工具，读取其 schema，使用当前记录版本提交到已选项目。写入后重新读取，核对图源、模块和核对信息与本次提交一致。冲突时重读并比较用户或其他 Agent 的修改，决定如何合并。

当前工具缺少架构持久化能力时，把架构草稿写到用户指定的工作文件位置，未指定时使用已明确确认的代码目录下的 `docs/architecture.md`。在文件内容和完成回复中都标为「本地草稿，待发布到 Memory Master」，交付草稿路径和预览结果。项目存储的正式更新通过 Memory Master 写入流程执行。

交付时说明核对的代码范围、本次实质变化、仍待确认的关系，以及内容已保存到的具体位置。渲染或代码核对失败时保留草稿状态。
